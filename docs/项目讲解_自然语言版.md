# Olist 电商经营分析 Copilot：项目讲解

## 1. 我做的是什么

这是一个面向电商经营分析的项目。它把数据清洗、SQL 分析、可视化、机器学习和自然语言问答放在了同一个应用里。

我使用的是 Olist 巴西电商数据。用户可以先看到平台整体的订单量、支付金额、客单价、延迟率和评价情况，再继续往下分析地区、品类、卖家和履约表现。如果想问一个具体问题，也可以直接在 AI 助手里输入自然语言。

不过，这个项目的重点不是让大模型随便生成一段分析，而是保证每个结论都有数据依据。大模型只负责理解问题和组织语言，指标计算仍然交给固定的分析函数和 DuckDB 完成。

## 2. 我为什么这样设计

如果只做一个 Streamlit 图表页面，能够展示可视化能力，但很难说明我是否真正理解了数据处理和指标口径。

所以我把项目拆成几层：

```text
原始数据
  -> 数据清洗和校验
  -> DuckDB 分析仓库
  -> 指标和分析服务
  -> Streamlit 看板
  -> 延迟风险模型
  -> 受控式 AI 分析助手
```

这样做的好处是，数据、指标、模型和页面之间的关系比较清楚。以后替换数据源，或者增加新的分析指标，也不会需要重写整个应用。

## 3. 数据是怎么进系统的

项目支持两种数据来源。

真实数据放在：

```text
data/raw/
```

演示数据放在：

```text
data/demo_raw/
```

真实数据和演示数据分开，是为了避免演示脚本覆盖用户自己的数据。没有完整真实数据时，项目会使用固定随机种子生成的演示数据，所以别人拿到代码后也能运行出相同的结果。

数据管道主要在下面这个文件中：

```text
D:\个人简历\olist-analysis-copilot\src\olist_copilot\data_pipeline\pipeline.py
```

处理过程大致是：

1. 读取 CSV 或 Excel 文件；
2. 检查 Olist 标准字段是否齐全；
3. 统一时间字段和金额字段的格式；
4. 处理缺失的维度值；
5. 关联订单、商品、支付、评价、卖家和买家数据；
6. 生成订单分析表和商品明细表；
7. 写入 DuckDB，并导出 Parquet 中间文件。

另外，建仓时还会保存源文件的 SHA-256 指纹。源数据没有变化时，不需要重复建仓；源文件变化后，系统会自动识别并重新处理。

## 4. 为什么要保留两种数据粒度

这是项目里我比较重视的一点。

### 订单粒度

```text
mart_order_analysis
```

一行代表一个订单。它适合计算：

- 订单量；
- 客单价；
- 延迟率；
- 评价表现；
- 延迟风险预测。

### 商品明细粒度

```text
fact_order_items
```

一行代表一个订单中的一个商品。它适合计算：

- 品类销售额；
- 卖家销售额；
- 商品金额；
- 运费；
- 商品数量和重量。

不能把所有分析都放到订单表里。一个订单可能包含多个商品、多个品类，甚至多个卖家。如果直接把订单金额归到第一条商品明细，就会导致卖家和品类的销售额失真。

所以项目里规定：订单相关指标使用订单粒度，商品、品类和卖家相关分析使用明细粒度。

## 5. 看板做了什么

看板入口是：

```text
D:\个人简历\olist-analysis-copilot\app.py
```

分析逻辑主要放在：

```text
D:\个人简历\olist-analysis-copilot\src\olist_copilot\analytics\services.py
```

页面上主要有几类内容：

### 经营总览

展示订单量、支付金额、客单价、延迟率和平均评价，让用户先了解整体情况。

### 趋势分析

按月份查看订单量和销售额的变化，观察业务是否有明显的增长或波动。

### 地区和品类分析

通过排名和图表查看哪些地区、品类的订单和销售表现更好，也可以对比延迟率。

### 卖家表现

使用商品明细粒度数据分析卖家的销售额、订单量和履约情况。

页面本身不直接写很多 SQL。它调用分析服务，分析服务再从 DuckDB 读取数据。这样看板和 AI 助手可以复用同一套分析逻辑，不容易出现两个页面指标不一致的问题。

## 6. 延迟风险模型怎么做

模型要回答的问题是：

> 订单产生时，能不能根据当时已经知道的信息，判断它之后是否可能延迟？

项目把实际送达时间晚于预计送达时间的订单标记为延迟订单，生成 `late_flag` 标签。

模型使用的特征包括：

- 商品金额；
- 运费；
- 订单商品数量；
- 商品平均重量；
- 买卖双方地区；
- 是否跨州；
- 预计配送天数；
- 下单月份；
- 支付方式。

我特意排除了实际送达时间、评价分数和最终履约状态。这些字段在预测时已经属于结果信息，如果把它们放进特征里，模型分数可能很好看，但没有实际意义。

模型默认使用 Logistic Regression 作为可解释的基线模型，同时保留了 Random Forest 的支持，方便比较线性模型和非线性模型。

训练集和测试集不是随机切分，而是按照订单购买时间切分。较早的订单用于训练，较晚的订单用于测试，这样更接近真实的线上预测场景。

## 7. AI 助手为什么不是直接生成 SQL

用户可以输入类似这样的问题：

```text
哪些地区的订单延迟率最高？
```

系统不会把这句话直接交给大模型，然后让大模型自由生成 SQL。实际流程是：

```text
自然语言问题
  -> 意图解析
  -> 指标和维度校验
  -> 调用白名单分析函数
  -> DuckDB 计算真实结果
  -> 大模型解释结果
```

例如，系统会把问题解析成：

```json
{
  "intent": "ranking",
  "metric": "late_rate",
  "dimension": "customer_state",
  "limit": 10
}
```

然后检查这些字段是否在允许范围内。如果指标、维度或查询数量不合法，系统会拒绝执行。

大模型在这里主要做两件事：

1. 理解用户想分析什么；
2. 根据已经计算出来的结果，写出比较容易读懂的解释。

核心数字不是大模型编出来的，而是来自指标层和 DuckDB 查询结果。没有 API Key 时，项目还可以使用本地模板继续运行。

## 8. A/B 测试模块的边界

项目使用 SciPy 做比例检验，可以输入两组样本数和转化人数，计算转化率、提升幅度和 p-value。

但 Olist 数据本身不是随机实验数据，所以我没有把普通的组间差异直接说成因果关系。演示时我会说明：这个模块用于展示统计检验过程，真正的营销实验还需要随机分组和实验设计。

## 10. 我是怎么使用 Codex 的

我没有把 Codex 当成一个只负责生成代码的工具，而是把它放进了开发流程里。

具体做法是：

1. 先根据岗位 JD 拆出数据分析、SQL、机器学习和 AI 应用能力；
2. 再把需求拆成数据管道、指标层、分析服务、模型、AI 编排和展示层；
3. 先写测试，确定数据生成、指标口径、模型防泄漏和 AI 参数校验的行为；
4. 再逐步实现功能；
5. 用演示数据跑完整流程；
6. 最后做语法检查、测试和代码审查。

面试时我不会只说“这个项目是 Codex 帮我写的”。更准确的说法是：

> 我使用 Codex 辅助完成需求拆解、测试设计和代码审查，但项目的业务口径、数据粒度、模型特征和 AI 安全边界是我自己确定的，代码也经过了本地复现和验证。

## 11. 面试时怎么介绍，控制在一分钟

> 我做了一个 Olist 电商经营分析 Copilot，想解决的是从原始订单数据到经营结论之间的整套分析问题。项目使用 Pandas 做多表清洗，用 DuckDB 建本地分析仓库，再通过 Streamlit 和 Plotly 展示订单、销售、地区、品类和卖家表现。

> 在数据建模上，我区分了订单粒度和商品明细粒度。订单粒度用于订单量、延迟率和模型，明细粒度用于品类和卖家分析，避免多卖家订单被错误归因。

>
> 整个项目包含演示数据、建仓脚本、测试和文档，可以在本地复现。

## 13. 需要真正掌握的重点

我不需要一开始就把每个函数都背下来，但下面几件事要能解释清楚：
