# Olist 电商经营分析 Copilot：简历项目说明（STAR 版）

## 一、推荐写法

### 项目名称

**Olist 电商经营分析 Copilot**

### 技术栈

Python、Pandas、NumPy、SQL、DuckDB、Parquet、Streamlit、Plotly、Scikit-learn、SciPy、DeepSeek V4 Flash API、Pytest

### 简历项目描述

- **项目背景/任务：** 针对数据分析和 AI 应用岗位中对 Python、SQL、指标体系、BI 看板、机器学习和大模型应用的综合要求，基于 Olist 巴西电商多表数据，搭建一套可复现的经营分析工具。
- **数据与分析：** 使用 Pandas 完成 CSV/Excel 数据接入、字段校验、时间和金额清洗，使用 DuckDB 构建分析仓库，并分别维护订单粒度分析表和商品明细表，解决多商品、多品类、多卖家订单的归因问题；通过统一指标层沉淀订单量、支付金额、客单价、延迟率和卖家表现等指标，供看板和 AI 助手复用。
- **模型与 AI：** 基于订单早期可获得的金额、运费、商品数量、地区和预计配送时间等特征，使用时间切分训练 Logistic Regression 延迟风险模型，并排除实际送达时间、评价分数等结果字段以避免数据泄漏；实现受控式自然语言分析流程，通过意图解析、指标/维度白名单和参数校验调用固定分析函数，再由 DeepSeek V4 Flash 根据真实查询结果生成解释，无 API Key 时支持本地降级。
- **项目结果：** 使用 Streamlit 和 Plotly 完成经营看板，覆盖趋势、地区、品类、卖家和履约分析；使用 SciPy 补充 A/B 测试计算，并编写 22 项 Pytest 测试覆盖数据管道、指标口径、数据仓库、模型训练和 AI 安全护栏，形成可本地复现、可演示、可继续扩展的分析项目。

## 三、严格按 STAR 拆解

### S：Situation，项目背景

广州数据分析和 AI 应用岗位的 JD 普遍同时关注 Python、SQL、数据清洗、可视化、指标体系和机器学习；部分岗位还要求使用大模型或 AI 工具提升分析效率。单独做一个静态看板只能体现展示能力，单独做一个聊天机器人又缺少真实业务数据和指标口径。

因此，我选择 Olist 电商数据作为业务场景，把传统数据分析和 AI 辅助分析放到一个项目中。

### T：Task，项目目标

项目需要解决四件事：

1. 将多个 Olist 数据表整理成可查询、可复现的分析数据集；
2. 建立稳定的业务指标口径，并在看板和 AI 助手中复用；
3. 用一个实际业务问题展示机器学习能力，而不是只调用现成模型；
4. 让 AI 的输出有数据依据，同时限制任意 SQL 和不合法参数。

### A：Action，具体行动

#### 1. 搭建数据处理和仓库层

使用 Pandas 支持 CSV/Excel 接入，对字段、时间、金额和缺失值进行处理；使用 DuckDB 保存分析表，并将 Parquet 作为中间层。

在建模时保留两种粒度：

- 订单粒度：用于订单量、客单价、延迟率和模型；
- 商品明细粒度：用于品类、商品和卖家销售额。

这样避免一个订单包含多个卖家时，把整笔订单错误算给第一条商品明细。

#### 2. 建立指标和分析服务

把订单量、支付金额、客单价、延迟率、平均评价等指标集中维护，页面不直接重复实现计算逻辑。看板和 AI 助手都调用分析服务，减少不同模块之间的口径差异。

#### 3. 完成延迟风险建模

以实际送达时间是否晚于预计送达时间作为标签，使用商品金额、运费、商品数、地区和预计配送时间等订单早期信息构造特征。

使用 Logistic Regression 作为可解释基线模型，同时支持 Random Forest；按照订单购买时间进行训练集和测试集切分，排除实际送达时间、评价分数和最终状态等结果字段。

#### 4. 增加受控式 AI 分析

用户可以用自然语言提问，例如“哪些地区的订单延迟率最高”。系统先将问题解析为意图、指标、维度和限制数量，再经过白名单和参数校验，调用固定分析函数获取结果，最后交给 LLM 生成解释。

模型不直接执行任意 SQL。没有 API Key 时，系统使用本地模板继续运行。

#### 5. 做测试和复现设计

用固定随机种子生成演示数据，隔离真实数据目录和演示数据目录；使用源文件指纹判断仓库是否需要重建；编写 22 项 Pytest 测试，覆盖数据管道、指标计算、仓库读写、模型防泄漏和 AI 参数校验。

### R：Result，项目结果

- 形成从原始多表数据、清洗、建仓、指标计算到可视化和 AI 问答的完整本地运行流程；
- 看板和 AI 助手共用指标与分析服务，避免同一个指标在不同页面出现不同口径；
- 模型只使用预测时可以获得的信息，并通过时间切分降低未来信息泄漏风险；
- AI 助手能够在受控范围内回答经营分析问题，同时保留查询结果作为解释依据；
- 项目包含 20 项自动化测试、演示数据、建仓脚本、数据字典、架构文档和模型报告，可以直接用于面试演示和项目复现。

## 四、面试中可以这样讲

> 我做的是一个 Olist 电商经营分析 Copilot，主要是为了把数据分析和 AI 应用结合起来，而不是单独做一个静态看板。
>
> 我先用 Pandas 清洗 Olist 的订单、商品、支付、评价和卖家等多表数据，再用 DuckDB 建分析仓库。这里我区分了订单粒度和商品明细粒度，订单相关指标用订单表，品类和卖家销售额用明细表，避免多卖家订单被错误归因。
>
> 在此基础上，我做了统一指标层和 Streamlit 看板，还用订单早期特征训练了一个延迟风险模型。为了避免数据泄漏，我没有使用实际送达时间和评价分数，并且按照订单时间切分训练集和测试集。
>
> AI 助手部分，我没有让大模型直接生成和执行任意 SQL，而是先解析问题，校验指标和维度，再调用固定的分析函数，最后让模型解释真实结果。整个项目有演示数据、自动化测试和文档，可以本地复现。

## 五、不同岗位的侧重点

### 投数据分析岗

优先强调：

- Pandas 数据清洗；
- SQL 和 DuckDB；
- 指标体系；
- 订单与商品明细建模；
- Streamlit/Plotly 看板；
- 延迟率、客单价和卖家分析；
- Pytest 和可复现流程。

### 投 AI 应用岗

优先强调：

- 自然语言到结构化意图；
- 指标和维度白名单；
- 工具调用和查询编排；
- DeepSeek V4 Flash API；
- 本地降级机制；
- 大模型不直接执行任意 SQL；
- 结果证据和安全边界。

### 投数据模型或算法岗

优先强调：

- 延迟标签设计；
- 特征工程；
- 时间切分；
- 数据泄漏控制；
- Logistic Regression 与 Random Forest 对比；
- Precision、Recall、F1 和 ROC-AUC 评估。
